The problem — and who has it

Small merchants check orders and inventory by hand across several admin pages. Generic AI chat either cannot see the data or makes numbers up — and an agent with write access is a risk.

Who has this problem: store owners and ops staff without an analytics team.

Technical decisions

The model cannot write GraphQL

It chooses from typed tools with strict schemas. Unknown tools are rejected; at most 8 tool calls per question.

Numbers are verified by code

The final answer must list each figure with its period and source step; a check compares every number in the text with the tool results.

Proposals can only target what was seen

Write tools accept only IDs returned by read tools in the same run, so an instruction inside an order note cannot point the agent at an arbitrary product.

Safe writes

Inventory changes use @idempotent with the proposal ID and changeFromQuantity, so a double click or a stale view cannot apply twice or overwrite a newer stock count.

Home without AI

The dashboard calls the same tools directly — fast, free and exact.

Trade-offs I accepted

  • Order scans stop at 1,000 orders per question and 60 days without read_all_orders; larger shops need ShopifyQL or bulk operations.
  • Rejecting answers with unverifiable numbers will sometimes hide a correct rounded figure. Showing a warning is better than showing a wrong number.
  • The weekly summary (nice-to-have) is not built yet.

What was missed — and what I learned

  • Agent misses: not measured yet — this app has not been through Agent Review.
  • The production build failed because a client component imported a constant from a server-only module. Type-checking passed; only the build caught it. Lesson: always run the real build, not just tsc.
  • BFS 5.3.1 (Web Pixel for Analytics apps) was added to the project 01 rule set from day one, because this app could be listed under Analytics.
